# v0.3.0 Runnable Demo and Community Launch Design

**Status:** Proposed for maintainer review

**Date:** 2026-08-12

**Target repository:** `1348109517/abaqus-agent-skills`

**Target release:** v0.3.0

## Summary

v0.3.0 will evolve Abaqus Agent Skills from a documentation-first collection
into a documentation-first collection with a small, runnable reference demo.
The demo will let an Abaqus or finite-element-analysis practitioner inspect a
fully synthetic engineering contract, run deterministic static checks without
Abaqus, and receive an auditable Markdown and JSON report.

The release will also add the minimum project metadata and contribution paths
needed for a responsible community launch. Promotion will begin only after the
runnable experience and release checks pass. Posts will invite technical
feedback and contributions; they will not buy, exchange, or solicit artificial
GitHub stars or imply adoption that has not occurred.

## Audience and problem

The primary audience is Abaqus and finite-element-analysis users who automate
model construction or review with Python and AI coding agents. The repository
currently explains seventeen workflows, but a new visitor still has to imagine
how the skills work together. This creates three barriers:

1. There is no one-command experience that demonstrates the repository's
   evidence boundaries.
2. A visitor cannot quickly distinguish a naming or dependency failure from a
   solver or engineering-validity claim.
3. A community post has no concrete result for readers to reproduce before
   deciding whether the project is useful.

## Goals

- Provide a useful first result within three minutes of cloning the repository.
- Demonstrate a cross-skill Abaqus review workflow using public synthetic data.
- Produce stable, human-readable and machine-readable audit reports.
- Preserve the separation between static checks, solver completion, physical
  review, and engineering claims.
- Run on Python 3.10 or newer with no third-party packages and no Abaqus
  installation.
- Add clear citation, contribution, issue, and pull-request paths.
- Support an honest, staged launch to specialist and open-source communities.

## Non-goals

- Running Abaqus/CAE, an Abaqus solver, or `abqpy`.
- Parsing arbitrary production `.cae`, `.odb`, or `.inp` files in v0.3.0.
- Certifying model physics, numerical convergence, or engineering safety.
- Publishing private project data, private paths, unpublished research, or
  uncertain upstream content.
- Claiming broad adoption, production readiness, or official SIMULIA support.
- Automating public posts or asking users to vote for, star, or endorse the
  repository.

## Alternatives considered

### Documentation-first expansion

Adding more guides and cross-links would preserve the current architecture and
be inexpensive, but it would not give a visitor a reproducible result to try.
It was rejected as the primary v0.3.0 direction; documentation improvements
remain supporting work.

### CLI-first toolkit

Building a general-purpose Abaqus audit CLI could create a larger feature
surface, but it would blur the repository's documentation-first identity and
introduce premature schema and compatibility commitments. It was rejected for
v0.3.0. The approved runner is intentionally a bounded reference demo.

### Runnable-demo-first release

The selected approach adds the smallest executable layer that demonstrates how
multiple skills compose, while retaining clear non-solver boundaries. It gives
specialist readers something concrete to reproduce and creates evidence for a
technical tutorial without claiming a production parser or validator.

## Design principles

1. **Documentation remains primary.** The runner illustrates the skill
   contracts; it does not turn the repository into an Abaqus replacement.
2. **Synthetic by construction.** Every example value is invented for this
   repository and is safe to redistribute.
3. **Deterministic and inspectable.** The same input must produce the same
   ordered findings and report text.
4. **Evidence gates are explicit.** A static pass never implies execution,
   physical validity, or a publishable engineering claim.
5. **No-dependency quickstart.** Standard-library Python minimizes setup and
   makes CI behavior match the local demo.
6. **Promotion follows utility.** Community communication begins after a tagged
   release with a reproducible experience.

## User experience

The primary command will be intentionally simple:

```bash
python scripts/run_demo.py
```

It will run the complete synthetic scenario and write reports beneath a
gitignored output directory. Named scenarios will also be available:

```bash
python scripts/run_demo.py --scenario naming-drift
python scripts/run_demo.py --scenario evidence-overreach
```

The command will print:

- the selected scenario;
- the input contract path;
- a count of `PASS`, `WARNING`, and `REVIEW_REQUIRED` findings;
- the Markdown and JSON report paths; and
- a reminder that no solver or physics validation occurred.

The command exits with status 0 when the runner completes, including scenarios
that intentionally contain review findings. Invalid files or internal runner
errors exit nonzero. This keeps expected teaching failures distinct from tool
failures.

## Synthetic model contract

The JSON contract will contain only the fields required to demonstrate the
workflow:

- schema version and scenario identifier;
- declared unit system;
- model, part, instance, set, and surface names;
- material and section assignments;
- ordered analysis steps;
- boundary conditions and loads with referenced regions and steps;
- mesh intent and element-family declarations;
- interactions with referenced surfaces;
- requested field and history outputs;
- evidence status declarations.

References will use stable identifiers rather than positional indexes. The
contract will be deliberately smaller than a general Abaqus schema. Unknown
fields may be retained for forward compatibility, but missing required fields
will be reported deterministically.

## Checks and findings

The first release will implement checks that map directly to existing skills:

- required top-level contract fields;
- explicit units and nonempty identifiers;
- unique object names within each namespace;
- references to existing parts, instances, sets, surfaces, materials, steps,
  and outputs;
- valid step ordering for loads and boundary conditions;
- presence of a mesh intent and explicit element-family declaration;
- interaction regions that resolve to declared surfaces;
- output requests that support the scenario's stated review intent; and
- evidence declarations that do not skip from static review to physical or
  engineering approval.

Each finding will have a stable code, severity, message, contract location,
related skill, and suggested next action. Status meanings are:

- `PASS`: the declared static contract satisfies that check.
- `WARNING`: information is incomplete or deserves attention but the static
  contract can still be reviewed.
- `REVIEW_REQUIRED`: a dependency is broken or an evidence boundary is crossed;
  a person must resolve it before a later workflow stage.

No finding may use `PASS` to describe solver completion or physical validity.

## Scenarios

### Complete contract

A compact tunnel-and-soil model contract with internally consistent synthetic
names and a bounded review intent. It demonstrates the happy path while still
ending at the static-review gate.

### Naming drift

One or more loads, interactions, or outputs reference a renamed region. The
report must identify the unresolved reference, its consumer, and the most
relevant naming or dependency skill.

### Evidence overreach

The contract declares an engineering-ready conclusion without solver evidence
or physical review. The report must mark the claim `REVIEW_REQUIRED` and explain
the missing gates without making a physics judgment.

## Reports

The JSON report is the canonical machine-readable artifact. It will include the
runner version, scenario, input digest, summary counts, ordered findings, and an
evidence-boundary disclaimer. The Markdown renderer will use the same finding
objects so the two formats cannot drift.

Generated output will not be committed, except for small expected fixtures used
by tests and documentation. Reports must contain no timestamps by default so
snapshot tests remain deterministic. An optional runtime timestamp may be added
later outside the canonical comparison path.

## Installation and contribution experience

v0.3.0 will add a small standard-library installer/helper that can list skills,
validate a requested skill name, and copy one complete skill directory to an
explicit target. It must never guess or overwrite a destination silently.
Dry-run behavior and collision reporting are required before a real copy.

The repository will also add:

- `CITATION.cff` with truthful project and release metadata;
- issue templates for bug reports, skill proposals, and synthetic examples;
- a pull-request template with validation and clean-room checkboxes;
- an expanded contributing guide for synthetic examples and compatibility
  evidence; and
- a README quickstart that links the demo, compatibility boundary, and first
  contribution routes.

## Testing and CI

Implementation will use unit tests and end-to-end command tests. CI must verify:

- the existing seventeen-skill repository contract;
- contract loading and deterministic ordering;
- all three scenario outcomes;
- agreement between JSON and Markdown summary counts;
- nonzero exits for malformed input and internal errors;
- no overwrite in installer dry-run and collision cases;
- relative link integrity and clean-room sensitive-text checks; and
- successful execution on supported Windows and Linux Python versions.

The test suite must not require Abaqus, network access, credentials, or private
files. A release candidate is not complete until the documented commands have
been run from a clean checkout.

## Documentation and presentation

The English README remains the primary landing page, with the Chinese README
kept aligned for scope and quickstart claims. The demo guide will explain the
data flow, each scenario, finding codes, and the evidence boundary. A compact
architecture diagram may be included, but screenshots will not substitute for
copyable commands and text output.

The initial public tutorial will be based on the complete and naming-drift
scenarios so readers can reproduce every shown result. Promotional material
must link to the tagged release or stable default branch, not an unmerged work
branch.

## Community launch plan

Promotion will proceed in four stages.

### Stage 1: specialist communities

Publish a technical walkthrough to the SIMULIA Community. Before posting to an
Abaqus or FEA subreddit, check the current rules and, when promotional status
is unclear, ask moderators. The post will disclose that it is written by the
maintainer and that the project is early-stage and independent.

### Stage 2: reproducible English tutorial

Publish an original DEV Community article showing the synthetic contract,
naming-drift finding, and evidence boundary. The call to action will request
technical feedback, bug reports, and additional synthetic scenarios.

### Stage 3: open-source and agent communities

Share a concise, channel-specific version in communities that explicitly allow
free open-source project posts or provide a self-promotion thread. Avoid copied
mass posts and disclose maintainer affiliation.

### Stage 4: Show HN, only when ready

Consider Show HN only after a fresh visitor can try the nontrivial demo without
signup. Follow its title and participation rules and do not ask friends or
readers to upvote or comment.

Every external post is a separate public action. Before it is published, the
maintainer will review the exact site, account, title, body, links, and any
images. No automatic cross-posting is in scope.

## Ethical growth boundary

Allowed growth work includes original tutorials, specialist discussion,
transparent maintainer posts, issue responses, contributor support, and
submissions to relevant directories that accept project proposals.

The following are prohibited:

- buying, trading, or coordinating stars, votes, comments, or followers;
- fake or secondary accounts used to simulate adoption;
- unsolicited mass messages or identical cross-post spam;
- hiding the maintainer relationship;
- asking for a star as a condition of access, support, or reciprocity; and
- describing download, usage, or ecosystem impact without evidence.

## Measurement

The first launch cycle will run for fourteen days. A short public launch log
will record the release URL, published channels, dates, and corrections. The
maintainer will evaluate:

- reproducible bug reports and substantive comments;
- new synthetic use cases or contribution proposals;
- forks and pull requests;
- release or repository traffic when GitHub makes it available; and
- stars as one secondary discovery signal, never as proof of engineering value.

Results will be reported factually. Zero activity on one channel is a signal to
improve fit or documentation, not permission to manufacture engagement.

## Release gates

v0.3.0 may be tagged only when all of the following are true:

1. A clean clone on Python 3.10+ runs `python scripts/run_demo.py` without
   third-party dependencies.
2. All three scenarios generate the expected deterministic findings and both
   report formats.
3. Windows and Linux CI pass the full repository and demo tests.
4. README claims match actual behavior and retain the independence disclaimer.
5. Public files pass sensitive-data and link checks.
6. Citation and contribution metadata are valid.
7. The release notes state what the demo does and explicitly does not validate.
8. Draft promotion copy links to reproducible public artifacts and makes no
   adoption claim.

## Implementation sequence after design approval

1. Write a file-by-file implementation plan with test-first checkpoints.
2. Add failing tests for the JSON contract, findings, reports, and CLI.
3. Implement the standard-library demo core and three synthetic scenarios.
4. Add installer/helper tests and implementation.
5. Update documentation, community templates, and citation metadata.
6. Run local and CI validation from a clean checkout.
7. Review, merge, tag v0.3.0, and publish release notes.
8. Prepare each community post for maintainer approval before publication.

Implementation and public posting are outside this design commit and begin only
after the maintainer approves this written specification.
